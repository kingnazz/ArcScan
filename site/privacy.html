Privacy

What ArcScan sends, and what it keeps.

ArcScan is a local-first tool, and this page states precisely what that means rather than leaving it as a slogan. It covers the desktop application v1.8.5 and this website.

The short version

Your scan results, device inventory, names and notes stay on your computer by default. If you explicitly connect ArcScan to an ArcAtlas server and confirm a send, the selected network inventory is sent to that server's Discovery inbox. Nothing is sent automatically after a scan. The Installed edition can make an optional update check. Both editions offer a public IP lookup that only runs when you press Check.

What stays on your computer

Everything ArcScan discovers is written to a local SQLite database. Installed ArcScan keeps that database in the operating system's application-data directory. Portable uses a fresh private database for the current process and removes it during safe session cleanup. Database contents are not transmitted in the background. The explicit ArcAtlas handoff described below is the only feature that sends selected inventory data to a server.

  • Scan results: addresses, hostnames, MAC addresses, manufacturers and open services.
  • The device inventory, including first-seen and last-seen dates.
  • Names you give devices, their status, and your notes.
  • Scan history and the comparisons between scans.
  • Your preferences, which are stored separately by the application window.

The Installed database lives at %APPDATA%\com.arcscan.app\arcscan.db on Windows and ~/Library/Application Support/com.arcscan.app/arcscan.db on macOS. It is an ordinary SQLite file: you can copy it, back it up, inspect it or delete it.

The portable Windows edition

The Portable Windows edition is disposable. Every process creates a unique session under <system temp>/ArcScanPortable/sessions/<unique-session-id>/. The session contains the regular SQLite database, a dedicated WebView profile and validated ArcScan ownership metadata. Inventory, History, Changes, device edits, discovery and preferences work normally while the process is open.

On normal shutdown ArcScan closes SQLite and the WebView, then removes the validated session it owns. A later Portable launch removes stale owned sessions left by a crash or failed cleanup. This deletion is restricted to the exact Portable namespace and requires a valid matching ownership marker, an inactive lock and only known ArcScan contents. Unknown directories, malformed markers, links and active sessions are not removed.

Portable does not intentionally retain its database, Inventory, History, Changes, names, notes, discovery evidence or WebView-backed preferences between launches. CSV, JSON and XML exports saved outside the session are the intentional exception and survive cleanup. The folder containing ArcScan.exe does not need to be writable, and Portable never falls back to Installed AppData or the Installed WebView profile.

Installed and Portable ArcScan are independent and may run together. Two Portable processes also receive independent sessions. To be precise about the cleanup claim: it covers state ArcScan owns. Windows and WebView2 may keep ordinary operating-system records of programs that ran, and no application controls all of those.

Requests the application makes

ArcAtlas direct handoff

Version 1.8.5 adds an optional direct handoff to ArcAtlas. ArcScan never sends inventory merely because a scan completed. A technician must first configure an ArcAtlas server and connection token, choose one network in Inventory, review the destination and device count, and press Send to ArcAtlas.

That explicit action sends the selected network's existing Inventory JSON fields over HTTPS to /api/discovery/arcscan on the server you configured. The ArcAtlas server therefore receives the inventory data in that handoff and ordinary HTTPS request metadata such as your public IP address. ArcScan does not contact an ArcAtlas server in the background, on a timer, or after a scan without that confirmation.

Installed ArcScan stores the ArcAtlas connection token in the operating system credential store and keeps only non-secret destination metadata in its application-data directory. Portable stores both the token and connection metadata in process memory only, so they disappear when the Portable process exits. The full token is never returned to the webview after setup, never logged, and never placed in a URL. Disconnecting locally removes the local secret but does not revoke the token on the ArcAtlas server.

Update check

When enabled, Installed ArcScan asks GitHub on launch whether a newer signed release exists by requesting the Installed update manifest. The request carries only what any HTTPS request carries, plus the version being checked. It does not include your scan targets, results or any identifier.

GitHub receives ordinary request metadata for this, including your IP address, as it would for any file you download from it. You can switch the check off in Settings, Network requests, and Installed ArcScan will then never contact the update feed on its own. Portable does not run the Installer update check and cannot apply the NSIS updater; its download action opens the release page only when you choose it.

Public IP lookup

ArcScan can tell you the address your internet connection appears from. It never runs on its own. From version 1.8.1 the control sits on the Scan screen, beside the local network, and says Not checked until you press Check. It is not needed for scanning, and it can be switched off entirely in Settings, Network requests, which also lets you forget the current session's answer.

When you do, ArcScan requests https://api64.ipify.org and, if that does not answer, https://icanhazip.com. Those services see your public IP address, because that is what they exist to report back to you. Nothing else is sent: no scan target, no result, no device data, no inventory. The answer is held in memory for the current session only. It is never written to the scan database, never stored as inventory data and never included in an export, and it is forgotten when you close the application or press Forget.

Earlier versions of ArcScan performed this lookup automatically at startup. Version 1.7 changed that, because a network tool should not make an outbound request before you have asked it to do anything, and no version since has looked it up without being asked. Moving the control onto the Scan screen in 1.8.1 did not change that: nothing is looked up at startup, after a scan, when you switch views or on a timer.

Release downloads

When you download an Installer or Portable ZIP, or Installed ArcScan installs an update, the file comes from GitHub. GitHub receives the normal request metadata for a download, including your IP address, user agent and the file requested. ArcScan never re-hosts binaries, and this website never serves them itself.

What the scan itself sends, and to whom

A scan sends packets to the addresses you asked it to scan, and to nowhere else. For each address that means one ICMP echo request and a TCP connection attempt on each port the selected profile covers. ArcScan then reads your own computer's ARP table, which is a local operation involving no network traffic of its own.

Devices on the network you scan will see those probes, as they would from any network scanner. Nothing about the scan is reported to the ArcScan project or to anyone else.

Local device discovery

From version 1.8.2, a scan of a network this computer is attached to also asks that network what its devices are, using the two protocols devices already use to announce themselves:

  • mDNS. A multicast DNS query sent to 224.0.0.251 on the local link, asking which services exist and then asking about the ones it names.
  • SSDP. A multicast discovery query sent to 239.255.255.250 on the local link.
  • Device description pages. Where a device advertises a description address over SSDP, ArcScan reads it for the manufacturer and model. It connects only to an address on the network being scanned; public addresses, loopback, other private subnets, redirects and addresses carrying credentials are all refused, and the address that was checked is the one used.

Both queries carry a time-to-live of one, so they cannot leave the local link. A scan of a remote or routed target sends neither, and neither does a scan with discovery switched off in Settings. No credentials of any kind are sent, and no cloud service, lookup service or fingerprint database is contacted, there is none to contact. What ArcScan learns is what your devices announce to anyone on the network who listens, and it stays on your computer with the rest of your inventory.

Copy discovery details

From version 1.8.3, the device panel offers Copy discovery details, which builds a short summary of what ArcScan detected about one device and puts it on your clipboard so you can report a wrong detection. It is built on your computer and nothing is sent automatically: no upload, no file, no request.

It deliberately leaves out your notes, the MAC address, the serial number, the device's own identifiers, any address it advertises, its IPv6 addresses, the network name and any database identifier. The local address appears masked, as 192.168.x.x. What remains is the device type, how sure ArcScan was, and the services and model strings the device announced, which is what a classification problem can be fixed from. Where it goes after that is entirely your choice.

What ArcScan never collects

  • No telemetry, usage statistics, crash reports or feature analytics.
  • No account, email address, licence key or device identifier.
  • No background or automatic upload of scan results. ArcAtlas inventory is sent only after an explicit technician-confirmed handoff.
  • No advertising identifiers, and no third-party SDK of any kind.

This website

The site is static and hosted on GitHub Pages. It sets no cookies, uses no analytics, and loads no fonts, scripts or images from anywhere but its own origin.

It makes one request to api.github.com to read the latest release, so the download cards can show real file sizes and links. That call sends nothing about you beyond the request itself, and the page works fully without it. A Content-Security-Policy header on every page restricts network access to exactly that one host.

GitHub Pages operates the hosting and, like any web host, sees the requests your browser makes. That is outside the ArcScan project's control and is covered by GitHub's privacy statement.

Uninstalling

Uninstalling ArcScan removes the application. It does not delete your database, so your history, device names and notes survive a reinstall or an upgrade. To remove them, delete the database file at the path listed above.

The Portable Windows edition has nothing to uninstall. Close all processes launched from that copy, then delete the extracted folder. No Installer, service, scheduled task, ArcScan registry setting or Start-menu entry was created. The current validated temporary session is removed on normal shutdown; a stale ArcScan-owned session left by a crash is eligible for strict cleanup on a later Portable launch.

Responsible use

ArcScan performs read-only discovery: it never attempts a password, never sends an exploit, and has no stealth or evasion behaviour. Scan only networks you own or have been authorised to inspect. Scanning a network without permission may be unlawful where you are, whatever tool is used.

Changes to this page

If ArcScan's network behaviour changes, this page changes with it in the same release. The full history is in the repository, and the code that makes every request described here is in the source.
