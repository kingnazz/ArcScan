ArcScan 1.8.3

What's new in ArcScan 1.8.3

ArcScan 1.8.2 started asking your network what its devices are. 1.8.3 is about what happens next: you can correct what it decided, it shows you when the evidence behind an answer has gone quiet, and it can hand you a short redacted summary when it gets one wrong. Everything still happens on your own machine.

Version 1.8.3 · free and open source · Full technical release notes on GitHub

  • Local network only, and no credentials
  • Installs over 1.8.x and keeps everything

Your correction wins

When ArcScan is wrong, you can say so.

Every device now has a device type you can set yourself. Pick one from the list in the device panel and that is what ArcScan calls it, everywhere: in the table, in the type filter, in search and in every export.

  • Fifteen choices, including Automatic
  • Set from the device panel
  • Used by the table and the filter
  • In every export
  • Reversible at any time

The correction never changes what the device is. It changes what ArcScan calls it, and nothing else. The device keeps the same identity, the same network, the same first-seen date, the same trust status, the same notes and the same history. Nothing is merged, nothing is split, and no duplicate appears.

What ArcScan worked out for itself is kept underneath rather than replaced, so you can see what you overruled and change your mind later. Choosing Automatic again reveals whatever ArcScan currently thinks, which may have improved since you corrected it.

Unknown is a real answer. Choosing it is not the same as leaving the type on Automatic. It is you saying that ArcScan is wrong and that you cannot say either, and the next scan will not talk you out of it.

Correcting a type is an edit you made, not something that happened on your network, so it never appears in the Changes list. Neither does evidence simply getting older.

Evidence gets old

An answer from months ago should not look like one from today.

ArcScan does not watch your network. It learns when you run a scan, and in 1.8.2 an answer it heard once stayed authoritative for ever. Now it keeps track of what it has stopped hearing.

  • Current
  • Getting old
  • Stale
  • Counted in scans
  • Nothing deleted

Evidence goes stale after three scans in a row that could have heard it and did not. That last part carries the weight. A scan only counts if it actually finished, ran both discovery protocols, and found the device. A stopped scan, a scan of a remote network, a scan with discovery switched off, and a scan where the device simply was not there all count for nothing: a device that was unplugged has not stopped advertising.

It is counted in scans, not in days. A wall-clock age would say more about when you last ran ArcScan than about the device, so a device panel says last seen 4 discovery scans ago rather than a date.

Stale evidence is kept, shown and dated. It is never deleted. What changes is how much weight it carries: a device type resting entirely on evidence nothing has confirmed in three qualifying scans drops from high confidence to medium, and the panel says why. It does not drop further, and the device does not become something else. One scan that hears it again puts it straight back.

Better answers

More devices recognised, from the same evidence.

No new protocols, no new probes and no lookup service. Every improvement below comes from reading what ArcScan already collected in 1.8.2 more carefully.

Televisions and the things plugged into them

A television with casting built in is now told apart from the streaming stick plugged into it. An Apple TV is recognised as a media device rather than filed as a speaker for accepting AirPlay audio, and a television that accepts the same audio is still a television. Roku devices are recognised, and a Roku television reads as a television.

Printers, storage and network equipment

A storage appliance that shares files, comes from a storage maker and serves its own web console is now recognised with high confidence. A gateway that advertises only part of its UPnP description is still recognised as a router. An access point or switch is recognised as network equipment, unless it is also your gateway, in which case router is the more useful thing to say.

Names that read like names

A device whose advertised name is really a machine identifier no longer has that shown as its name. Service suffixes are trimmed, so Office Printer._ipp._tcp.local reads as Office Printer, and a manufacturer the model already mentions is not repeated. Names that genuinely contain numbers, such as Synology DS923+, are left exactly as they are.

Unknown is still a valid answer, and it is still preferred to a guess. A camera is still never called a camera at high confidence on a video stream alone. ArcScan does not identify every device, and it does not claim to.

Honest history

How much each scan actually managed.

A scan that heard nothing and a scan that could not listen look identical in a device list. History now tells them apart, in four words.

Complete, Limited, Skipped, Interrupted

Complete means both protocols ran and finished, and the line shows what they heard. Limited means discovery ran but could not do all of it. Skipped means it did not run: a remote target, switched off, or no local network to send from. Interrupted means you pressed Stop while it was still going.

Only what ArcScan observed

When a pass was limited, the line names the one thing ArcScan actually saw: a socket that would not open, a response limit reached, a device page it refused to read. It never says a firewall blocked anything, because it cannot see your firewall and guessing would be worse than saying nothing.

Nothing is compared across a gap

A scan that could listen is still never compared with one that could not, which is the rule that stops a quiet scan from reporting that everything on your network disappeared. Older history is untouched and reads exactly as it did.

Reporting a wrong answer

Copy discovery details.

A new button in the device panel puts a short summary on your clipboard: what ArcScan decided, how sure it was, and the evidence behind it. It is meant for a bug report, and it is built for one.

What it leaves out

Your notes, the MAC address, the serial number, the device's own identifiers, the addresses it advertises and its full IP address. The local address appears masked, as 192.168.x.x, which says the kind of network without saying which device.

Where it goes

On your clipboard, and nowhere else. Nothing is uploaded, no file is written and no request is made. ArcScan tells you it copied, and then it is yours to paste wherever you choose, or not.

What it is for

A classification rule cannot be fixed from a screenshot of a device list. It can be fixed from the services and model strings a device advertises, which is exactly what this contains and nothing more.

Local only

It still asks your network, and nothing else.

1.8.3 adds no protocol, no probe and no outbound request. Every rule 1.8.2 stated is still exactly true, and is worth stating again.

Your network, or nothing

Discovery runs only when what you are scanning is inside a network this computer is actually attached to. Remote subnets, routed targets and public addresses never receive a single query. The queries carry a time-to-live of one, so they cannot leave the local link even if a router would have carried them.

No credentials, ever

ArcScan sends no username, no password, no community string and no key. It has none and asks for none. Everything it learns comes from what devices announce to anyone listening.

No service is contacted

There is no lookup service, no fingerprint database, no manufacturer API and no telemetry. Nothing about your network, your devices or your corrections is sent anywhere. The new diagnostic summary is built on your machine and goes on your clipboard.

Read-only, and bounded

ArcScan configures nothing and changes nothing on any device. Every part of discovery is bounded by a time budget and a count, so a broken or hostile network cannot make a scan run long. You can switch all of it off in Settings, and a scan then behaves exactly as it did before discovery existed.

Device pages are still checked before they are read

The rules that decide whether a device's description page may be read are unchanged. The address must be plain local HTTP, inside the network the scan actually ran against, with no redirect, no proxy and no second name lookup between the check and the connection.

Everything a device says is treated as text

Names, models and services come from unauthenticated devices, so they are bounded in length, stripped of control characters and displayed as text. A device that advertises markup gets its markup shown back to it as characters.

Upgrading

Install it over 1.8.x and carry on.

Everything you have is kept, and the first scan afterwards behaves like an ordinary scan rather than like a fresh install.

Your inventory is kept

Every scan, device, name, note, status, network, change and piece of discovery evidence survives without losing anything. The database gains two optional fields and nothing is rewritten, re-keyed or reclassified.

Your settings are kept

Discovery stays on if it was on and off if it was off, and every device keeps whatever type ArcScan had already worked out. Nothing arrives already marked stale, and no device arrives already corrected: the upgrade makes no choices for you.

No flood of changes

1.8.3 reads some advertised names more tidily than 1.8.2 did. Left alone, that would have reported a renamed device for every device whose name it improved, all at once. The first scan after upgrading compares names quietly for exactly that reason, and every scan after it compares them normally.

Unchanged

Everything 1.8.2 does, it still does.

This is a refinement release. Nothing about scanning, comparison or the shape of the app has moved.

The same four views

Scan, Inventory, Changes and History, in the same places, with the same keyboard shortcuts. No new primary view, and no second device panel.

The same scanning

The same ports and the same comparison rules. Partial scans still never mark a device missing, because a scan that was stopped did not look everywhere. Still IPv4 only, and the same exports plus four new columns. Device identity is still MAC first, then hostname and manufacturer, then address, and discovery still never decides it.

The same promises

No account, no cloud, no telemetry, no scheduled scans, no background scanning, no notifications and no agent. ArcScan runs when you run it.
